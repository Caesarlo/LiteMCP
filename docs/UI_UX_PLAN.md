# LiteMCP 管理后台 UI/UX 方案

> 状态：评审稿  
> 日期：2026-08-09  
> 适用范围：LiteMCP 管理后台第一版  
> 设计基线：React + TypeScript + Vite + HeroUI v3 + Tailwind CSS v4

## 1. 文档目的

本文在现有架构方案基础上，进一步明确 LiteMCP 管理后台的信息架构、页面布局、核心交互、视觉语言、状态表达和 HeroUI 组件使用方式，作为后续低保真原型、视觉设计和前端实现的评审基线。

本文不修改后端领域模型、API、安全边界和发布语义。以下文档仍是相关约束的事实来源：

- [00-overview.md](architecture/00-overview.md)：产品范围、逻辑架构和核心发布模型。
- [02-admin-auth.md](architecture/02-admin-auth.md)：管理认证、授权和 step-up 约束。
- [03-service-crud.md](architecture/03-service-crud.md)：服务 CRUD、版本、operation 和并发语义。
- [06-frontend.md](architecture/06-frontend.md)：前端技术栈、路由、状态和验收要求。
- [07-observability.md](architecture/07-observability.md)：运行状态、日志、指标和可观测性边界。

## 2. 产品体验定位

LiteMCP 管理后台应定位为高信息密度的开发者与运维控制台，而不是普通的表单型 CRUD 后台。

第一版核心用户任务是：

1. 发现和筛选服务。
2. 创建或配置 `http_api`、`mcp_http`、`stdio` 服务。
3. 观察构建、同步、校验和发布过程。
4. 判断服务当前是否真正可用。
5. 配置 Agent 鉴权并取得接入信息。
6. 管理权限、API Key 和服务生命周期。
7. 在失败、并发冲突或权限变化后安全恢复。

核心体验链路为：

```mermaid
flowchart LR
    A["服务市场"] --> B["创建或选择服务"]
    B --> C["配置服务"]
    C --> D["构建、同步或发布"]
    D --> E["验证运行状态"]
    E --> F["配置 Agent 接入"]
    F --> G["持续观察与排障"]
```

## 3. 设计原则

### 3.1 状态真实，而不是视觉上简单

界面必须分别表达以下状态，禁止合并成一个“启用”开关：

- `desired_status`：用户期望服务启用还是停用。
- `runtime_status`：服务当前真实运行状态。
- `generation/observed_generation`：运行面是否已经观察到最新配置。
- operation：构建或同步任务处于排队、运行、成功、失败还是被替代。
- active revision/toolset：Agent 当前实际使用的配置和工具版本。

### 3.2 下一步动作清晰

错误信息除了说明发生了什么，还要给出合理的恢复动作，例如：

- 查看活动
- 编辑配置
- 重新同步
- 重新构建
- 重新加载服务端版本
- 以最新版本为基线重新应用

### 3.3 渐进披露

首页优先回答“有哪些服务、现在能不能用”；详情页回答“为什么”；配置页和活动页再展示参数、generation、revision、toolset、reason code 等技术细节。

### 3.4 安全操作保持可见且可理解

权限不足时保留必要的只读上下文，并解释动作为什么不可用。删除、关闭鉴权、替换权限等敏感操作使用显式确认和 step-up，不依赖隐藏按钮作为安全边界。

### 3.5 桌面优先，但不牺牲窄屏任务

桌面端服务高密度运维场景；320 CSS px 宽度下仍应能够登录、查看服务、编辑常规字段、生成或吊销 Key。复杂 Schema 编辑器可以内部水平滚动，但页面本身不能产生双向滚动。

## 4. 全局信息架构

采用标准 SaaS/管理平台布局：**持久左侧导航栏（Sidebar）+ 顶部栏 + 面包屑 + 内容区**。这是既定决策，不再是待评审项——第一版就有服务市场、团队、用户管理、审计四个一级模块（后两者仅 admin 可见），侧边栏结构从第一天就要能容纳它们，避免后续从顶部单栏迁移到侧边栏产生一次导航体系重构。

### 4.1 侧边栏

结构自上而下：

- 顶部 LiteMCP 品牌 + 折叠/展开按钮。
- 一级导航项（HeroUI `Link`/`Disclosure` 组合实现，非组件库以外的自造导航）：
  - **服务市场**（默认展开，第一版最高频入口）。
  - **团队**：`/teams`，所有已认证用户可见（用于查看/申请加入自己相关的团队）。
  - **用户管理**：`/users`，仅全局 admin 可见；非 admin 不在侧边栏渲染该项，且路由本身也返回 404，双重防线，前端隐藏不是唯一安全边界。
  - **审计中心**：`/audit`，仅全局 admin 可见，同上双重防线。
  - 系统设置：第一版置灰/隐藏占位，展示"即将推出"，不做成死链接。
- 底部：当前用户摘要（头像、用户名、所属团队数）+ 展开菜单（个人设置占位、退出登录）。
- 折叠态只显示图标 + Tooltip；移动端（`< 1024px`）收起为可通过顶部汉堡按钮打开的 Drawer，不与内容区并列挤压宽度。
- 当前一级模块高亮态同时用背景色 + 文本，不单独依赖颜色。

### 4.2 顶部栏

顶部栏不再重复侧边栏已有的模块导航，只保留页面级上下文：

- 面包屑（含当前团队/服务名称，可点击返回上级）。
- 团队切换器：当用户属于多个团队时，用于把服务市场筛选到"当前团队"；全局 admin 额外看到"全部团队"选项。
- 全局平台状态入口，只有存在平台级降级时突出显示。
- 语言切换（中文/英文），与明暗主题切换相邻放置，切换后不刷新页面骨架，即时生效。
- 明暗主题切换。

### 4.3 路由与页面层级

```text
/login
/market
/market/new?type=http_api|mcp_http|stdio
/market/:serviceId
├── /config
├── /tools
├── /activity
├── /access
└── /permissions
/teams
/teams/:teamId
/users            # 仅全局 admin
/audit            # 仅全局 admin
```

服务详情的 Tabs 必须对应真实路由，支持刷新、复制链接、浏览器前进和后退。

### 4.4 页面宽度与布局

- 内容区（侧边栏之外）最大宽度建议为 1440px。
- 列表页采用全宽数据区域。
- 普通表单正文建议限制在 800–960px。
- Schema 编辑器使用全宽工作台布局。
- 页面标题、主要动作和状态摘要在不同页面保持一致位置。

## 5. 服务市场

### 5.1 页面目标

服务市场应让用户快速回答：

- 有哪些我能访问的服务？
- 哪些服务可用、异常或正在变化？
- 服务属于哪一种类型？
- 应该进入哪个服务继续处理？

### 5.2 页面结构

页面从上到下包含：

1. 标题、简短说明和"创建服务"主按钮。
2. 轻量统计条：当前范围内的服务总数、运行异常数（`degraded/unhealthy/failed` 合计）、进行中的构建/同步数。三个数字，非独立仪表盘页面，点击"运行异常"可直接把下方筛选切到对应 `runtime_status`；纯信息不做装饰性图表，符合第 3 节"状态真实"和第 13 节视觉克制原则。
3. 范围切换：当前团队（按归属 `team_id` 筛选）/ 全部我可见（按 [01-data-model.md](architecture/01-data-model.md) 5.12 的可见性公式，含对所有人开放的服务）/（全局 admin）全部团队，与顶部栏团队切换器联动；默认落在"全部我可见"，不默认收窄到当前团队，避免团队只是归属分类却在浏览体验上被误当成访问边界（第 19 章第 10 条）。
4. 搜索、类型、运行状态、鉴权方式和排序控件。
5. 筛选结果摘要和清除筛选动作。
6. 服务列表。
7. 游标分页区域。

桌面端使用语义 Table，建议列为：

| 列 | 内容 |
|---|---|
| 服务 | 名称、简短描述或标签 |
| 团队 | 归属团队名 + 访问范围徽标：`公开`（存在 `principal_type=everyone` 授权行）或 `受限`（不存在，仅授权名单可见） |
| 类型 | HTTP API、Remote MCP、STDIO |
| 运行状态 | 当前真实状态和 condition 摘要 |
| 期望状态 | 已启用或已停用 |
| 鉴权 | API Key、无鉴权、OAuth2 未开放 |
| 工具 | active 工具数量 |
| 更新时间 | locale 时间，支持查看 UTC |
| 操作 | 查看、编辑、启停和更多操作 |

团队名在"范围切换=当前团队"时可省略（同列值全相同，属于冗余信息），但访问范围徽标（公开/受限）任何范围下都保留——这是唯一能让用户一眼判断"这个服务谁能看到"的信号，不能因为省略团队名连带隐藏。

移动端切换为 Card 列表，字段顺序保持一致，不把桌面宽表直接塞入横向滚动区域。

### 5.3 状态表达

运行状态作为主状态；期望状态、配置收敛和 operation 作为辅助信息。例如：

```text
正在同步
期望启用 · Generation 7/8
旧版本仍在提供服务
```

当 `desired_status=enabled` 但 `runtime_status!=ready` 时，不显示绿色“已运行”。

### 5.4 列表状态

- 首次加载：使用与最终表格或卡片等高的 Skeleton。
- 后台更新：保留旧数据，仅局部显示“正在更新”。
- 无服务：解释当前尚无服务，并提供创建入口。
- 筛选为空：保留筛选条件，提供清除筛选动作。
- 请求失败：在列表区域内显示 Alert 和重试，不用 Toast 替代内容。

## 6. 创建服务向导

### 6.1 设计目标

向导应降低三类服务配置的理解成本，同时忠实反映“创建服务、修改权限、生成 Key”不是同一个原子事务。

### 6.2 建议步骤

1. 选择服务类型。
2. 基础信息与类型配置：新增归属团队选择（默认预填当前团队切换器所选团队；用户只能选择自己所属且 `active` 的团队，全局 admin 可选任意团队）和访问范围选择：
   - **开放给所有人**（默认，对应创建请求 `access.mode=everyone`）：提示"所有已认证用户都能只读查看此服务；写操作仍需单独授权"。
   - **仅限授权名单**（对应 `access.mode=restricted`）：切换后展开一个预填了"归属团队"一行的授权列表（`principal_type=team`），可增删更多 team/user 行；创建时至少保留一行，否则该服务创建后只有 creator 自己能看到，向导需要提示这一点并要求二次确认才允许提交空名单。
   两种模式都不影响写权限——写权限仍然只能通过创建后向具名用户显式授予 `editor`。
3. 工具与运行参数。
4. 检查并创建。

服务创建成功后进入完成页，再引导用户：

- 添加成员权限。
- 生成 API Key。
- 复制 Agent 接入配置。

### 6.3 进度导航

HeroUI v3 当前没有内置 Stepper，因此使用语义化有序列表自行组合：

- 当前步骤使用 `aria-current="step"`。
- 已完成、当前、未完成都有文字含义，不能只靠颜色。
- 移动端折叠为“第 N/4 步 + 当前步骤名称”。
- 上一步和下一步放在 sticky action bar。
- 每一步离开前完成 step 级校验。

### 6.4 类型差异

#### HTTP API

- 配置 base URL、TLS、timeout 和上游鉴权。
- 在创建阶段编辑完整 Tool Schema 与 HTTP binding。
- 合法请求可以同步创建并发布 active toolset。

#### Remote MCP

- 配置 server URL、transport、protocol preference、TLS 和 timeout。
- 工具由下游发现，创建阶段不伪造可编辑工具列表。
- 创建成功只代表同步任务已排队，不能立即显示 Ready。

#### STDIO

- 上传代码包并显示文件名、大小和摘要计算进度。
- 配置入口、runtime、公开/私密环境变量、资源、队列、egress，以及实例池大小/单实例并发（默认都是 1，UI 明确标注"调高并发要求你的工具代码支持并发调用"，不做成一个不起眼的数字输入框）。
- 创建成功后进入 build/probe/publish operation。

### 6.5 动作文案

按钮应描述真实副作用：

- “创建并发布”
- “保存并触发同步”
- “上传并开始构建”
- “重新构建”

避免在所有场景使用含义不明的“确定”或“保存”。

## 7. 服务详情工作台

### 7.1 工作台头部

服务详情顶部固定展示：

- 面包屑（含所属团队，可点击回到 `/teams/:teamId`）。
- 服务名称、类型和访问范围徽标（`公开`/`受限`，与市场列表同一套视觉语言）。
- 运行状态。
- 期望状态。
- generation 收敛情况。
- 发布状态（见 7.3a）。
- 当前用户在该服务上的角色：editor/viewer 直接显示角色名；来自 `principal_type=team` 授权行的显示"团队授权（只读）"；来自 `principal_type=everyone` 的显示"公开访问（只读）"——三者都是真实存在的记录，不是隐式推断，文案上也不含糊。
- 主要动作和更多操作菜单。

示例：

```text
Weather MCP                                      Remote MCP
正在同步 · 期望启用 · Generation 7/8
旧 active toolset 仍在提供服务

[查看活动] [重新同步] [更多操作]
```

### 7.2 Tabs

- 概览
- 配置
- 工具
- 活动
- Agent 接入
- 权限

窄屏时 Tabs 允许单轴滚动，并保持当前项可见。

### 7.3 概览页

桌面端使用两列布局：

- 左侧：运行状态、conditions、当前 operation、失败原因。
- 右侧：active config revision、active toolset、Agent endpoint、鉴权摘要。

概览页优先展示用户可采取的动作，底层 ID 和完整 reason code 可放入 Disclosure。

### 7.3a 发布状态可视化

[01-data-model.md](architecture/01-data-model.md) 已经定义了完整的 revision/toolset 状态机（`draft/validating/validated/active/rejected/superseded` 与 `staging/validating/validated/active/rejected/retired`），本节不改变该状态机，只是要求 UI 把它合成为一条用户能一眼看懂的"发布状态"条，放在工作台头部和概览页顶部，而不是让用户去分别理解 revision 和 toolset 两套独立状态。

合成规则（纯前端展示层逻辑，后端不新增字段）：

| 发布状态（展示） | 判定条件 | 视觉 |
|---|---|---|
| 尚未发布 | 无 `active_toolset_id`，且当前没有进行中的 build/sync | 中性 Chip，附"去配置"入口 |
| 发布中 | 存在 `queued/running` 的 build_run 或 tool_sync_run | 进行中 Chip + 链接到 Activity 对应 operation，禁止误标成功 |
| 已发布 | 存在 `active_toolset_id` 且最近一次 operation 是 `succeeded`／或 `http_api` 同步创建成功 | success Chip，附 active toolset 版本号；stdio/mcp_http 类型附加一句"表示 Schema 校验通过，不代表首次真实调用一定成功"——probe 阶段只探测 `tools/list`，不会替用户跑一遍业务逻辑，避免用户把"已发布"误解成"已验证可用" |
| 最近一次更新失败（旧版本仍可用） | 存在 `active_toolset_id`（说明历史上发布成功过），但最近一次 build/sync 是 `failed` | warning Chip，明确文案"上次更新失败，当前仍在提供旧版本"，不能显示笼统的"失败"掩盖"旧版本仍可用"这个关键信息 |
| 从未成功发布 | 无 `active_toolset_id` 且最近一次 operation 是 `failed` | danger Chip，文案"尚未发布成功"，与上一行区分，避免用户误以为服务完全不可用（可能只是还没配置完） |

这条状态是概览页和工作台头部的**主要视觉焦点之一**，与运行状态（`runtime_status`）并列但不合并——运行状态回答"现在能不能用"，发布状态回答"配置有没有生效"，两者在 stdio/mcp_http 场景下可能不一致（例如已发布但下游临时不可达），必须分开展示，符合第 3.1 节的状态真实原则。

### 7.4 配置页

配置表单按领域区块组织：

- 基础信息。
- 上游连接。
- 鉴权和秘密。
- 超时与资源。
- Agent 策略。

普通表单使用单列主结构，强相关短字段可以两列排列。每个区块使用 Fieldset 或 Card，不使用一张无限延伸的大表单。

秘密字段显示“已配置/未配置”，编辑时明确提供：

- 保持现有值。
- 设置新值。
- 清除现有值。

### 7.5 并发冲突

PUT 返回 `409 CONCURRENT_MODIFICATION` 时：

- 保留本地草稿。
- 在内容区显示服务器最新版本的脱敏摘要。
- 提供“重新加载并丢弃本地修改”。
- 提供“以最新版本为基线重新应用”。
- 禁止自动覆盖或自动重试 mutation。

## 8. Tool Schema 编辑器

### 8.1 工作台结构

桌面端采用三部分布局：

- 左侧：工具列表、搜索、新增和排序。
- 中间：结构化与 JSON 源码双视图。
- 右侧或底部：校验结果和 HTTP binding 摘要。

移动端将工具列表放入 Drawer，编辑主区保持单列。

### 8.2 双视图规则

- 两个视图编辑同一个 canonical document。
- 视图切换前执行 parse 和 validate。
- 校验失败时留在当前视图并定位错误。
- 结构化视图不支持但合法的字段必须原样保留。
- 使用“已保留高级字段”提示用户存在未直接展示的内容。

### 8.3 校验反馈

校验结果按层次展示：

1. JSON 语法、文档大小和深度。
2. MCP Tool 形状与名称唯一性。
3. JSON Schema 2020-12。
4. HTTP binding 引用、path placeholder 和秘密边界。
5. 整套工具交叉校验。

字段错误显示在对应控件附近，同时在顶部提供可跳转的错误摘要。未知 JSON Pointer 进入摘要，并显示 request ID。

### 8.4 组件边界

HeroUI 用于 Tabs、Form、Fieldset、TextField、Select、Disclosure、Alert 和按钮。代码编辑器、JSON Diff、Schema tree 和大型校验器使用独立懒加载模块，不用普通 TextArea 模拟完整编辑器。

## 9. Activity 与 operation

### 9.1 页面目标

活动页用于解释“发生了什么、当前执行到哪里、旧版本是否仍可用、用户接下来应该做什么”。

### 9.2 表现方式

第一版不依赖复杂时间轴组件，可用 Card、Disclosure 和 ProgressBar 组合：

- queued：等待执行。
- running：展示 build/sync/probe/publish 当前阶段。
- succeeded：显示完成时间和新的 active 版本。
- failed：显示稳定 error code、脱敏摘要和恢复动作。
- superseded：说明已有更新版本替代本次任务，不建议重试旧 generation。
- cancelled：说明取消来源和当前 active 状态。

### 9.3 两种失败

必须区分：

- operation 查询失败：保留最后已知状态，提示状态暂时无法更新并允许重试。
- operation 自身失败：停止轮询，展示失败结论和恢复动作。

失败时若旧 active 版本仍可用，应持续明确展示。

## 10. 团队、Agent 接入、API Key 与权限

### 10.1 Agent 接入

页面展示：

- `/mcp/{service_id}` endpoint。
- 当前鉴权模式。
- MCP client 配置示例。
- curl 结构示例。
- 复制按钮及准确的成功/失败反馈。

API Key 示例默认使用 `<YOUR_API_KEY>` 占位符。只有刚生成 Key 的一次性弹窗可以选择复制包含真实 Key 的完整片段。

### 10.2 一次性 API Key

- 明文只存在于创建成功后的局部 Modal state。
- 标题明确提示“关闭后无法再次查看”。
- 提供复制和手动选择两种方式。
- Clipboard API 失败时不能声称复制成功。
- Modal 关闭后立即清空 state 并卸载内容。
- Key 列表只显示 prefix、状态、创建/过期/最后使用时间和限流信息。

### 10.3 权限

权限页直接展示 [01-data-model.md](architecture/01-data-model.md) 5.12 `mcp_service_permission` 的真实记录，不做任何隐式聚合或推断——列表里的每一行都是一条可以被单独增删的数据库记录，包括"开放给所有人"。

- 页面顶部是一个独立、醒目的"开放给所有人"开关（对应是否存在 `principal_type=everyone` 记录）：开启时该服务对所有已认证用户只读可见；关闭时下方的授权列表才是唯一的可见性来源。这个开关本身就是在增删一条真实记录，不是一个额外的推断规则。
- 开关下方是授权列表，分两类行：`团队` 授权（`principal_type=team`，只能是 viewer）和`用户`授权（`principal_type=user`，可以是 viewer 或 editor）。两类都可以直接在列表里增删，不需要先理解"来源"这种抽象概念。
- viewer（不论来自哪一行）可以阅读可见内容，但不能提交写操作。
- 禁用动作旁应解释所需权限。
- 批量修改授权列表提交前展示变更摘要（新增/移除的具体行）。
- creator 的 `editor` 行使用不可移除标记，且不允许被降级为 `viewer`。
- 任何授权变更（含"开放给所有人"开关）都需要 step-up。
- 关闭"开放给所有人"且授权列表为空时，前端提前阻止提交并提示"这将导致除你之外没有人能看到此服务"，不等后端拒绝才提示。

### 10.4 团队管理（`/teams`、`/teams/:teamId`）

- `/teams` 列表：卡片或紧凑表格展示"我加入的团队"和（如平台允许自助加入）"可加入的团队"；全局 admin 额外看到全部团队和"新建团队"入口。
- `/teams/:teamId` 详情分为两块：
  - 团队信息：名称、描述、状态（active/archived），team admin 可编辑，archived 需要二次确认（archived 后不可再创建/转入服务或新增成员，但不影响已归属服务运行）。
  - 成员列表：姓名、角色（member/admin）、加入时间；team admin 可增删成员、调整角色；同 [02-admin-auth.md](02-admin-auth.md) 需要保留至少一个 team admin，移除最后一个 team admin 的请求前端提前禁用并说明原因，不等后端 403 才提示。
- 团队下的服务以只读列表形式展示（复用市场列表的行组件），点击进入服务详情，不在本页重复服务的编辑能力。
- 转移服务归属团队的入口放在服务详情"更多操作"，不放在团队页反向操作，避免两处都能改同一字段导致心智混乱。

### 10.5 用户管理（`/users`，仅全局 admin）

- 用户列表：用户名、全局角色（admin/user）、状态（active/disabled/locked）、所属团队数、最近登录时间。
- 创建用户、禁用/启用、修改全局角色均为 step-up 后可用的动作，参照 [02-admin-auth.md](02-admin-auth.md) 14 章。
- 禁用最后一个 active admin、修改自己的角色为非 admin 均在前端提前禁用并解释原因。
- 本页不提供密码重置的明文查看能力；重置成功只提示"已重置，用户需要用新凭据登录"，不回显新密码（新密码生成/传递方式由后端流程决定，UI 不假设可以显示明文）。

### 10.6 审计中心（`/audit`，仅全局 admin）

- 面向 [01-data-model.md](01-data-model.md) `audit_event` 的全局浏览视图，是服务级 Activity 页（构建/同步历史）之外唯一能回答"谁在什么时候做了什么"的入口。
- 筛选：时间范围、`actor`、`action`、`resource_type`、`service_id`、`team_id`、`result`。默认按时间倒序，游标分页，不做客户端全量加载后过滤。
- 列表列：发生时间（locale + 可查看 UTC）、actor、action、resource、result、reason_code、request_id（可复制）。不展示 `changes` 中的秘密字段（后端本就只记录 `changed=true`，前端不需要额外脱敏逻辑，但要防止把整段 JSON 未加处理地渲染成可展开详情时意外包含大字段）。
- 本页是只读页面，不提供任何写操作；不做导出功能的第一版承诺，如需导出按后续可选处理，避免在 UI 里许下未经安全评审的批量下载能力。

## 11. 危险操作与反馈层级

### 11.1 AlertDialog

用于：

- 删除或恢复服务。
- 吊销 API Key。
- 关闭 Agent 鉴权。
- 破坏性权限变更。

确认文案包含对象名称和真实影响。需要输入名称确认的场景只用于高风险且难恢复的操作，避免滥用。

### 11.2 Modal

用于：

- Step-up 重新认证。
- 一次性 API Key 明文。
- 需要短期聚焦完成的非破坏性任务。

### 11.3 Toast

Toast 仅用于不需要立即处理、且页面中另有持久结果的反馈，例如“筛选已清除”或“配置已保存”。以下内容不能只用 Toast：

- 表单错误。
- 构建或同步失败。
- 鉴权风险。
- API Key 明文。
- 并发冲突。
- 删除结果和恢复路径。

## 12. HeroUI v3 组件映射

当前方案基于 HeroUI v3.0.5 的组件能力。

| 场景 | 推荐组件 |
|---|---|
| 侧边导航 | Link、Disclosure、Tooltip（折叠态）、Avatar（底部用户摘要） |
| 服务列表 | Table、Pagination、Skeleton |
| 移动端服务项 | Card、Chip、Dropdown |
| 页面与详情导航 | Breadcrumbs、Tabs、Link |
| 搜索和筛选 | SearchField、Select、TagGroup |
| 普通表单 | Form、Fieldset、TextField、TextArea、NumberField |
| 状态表达 | Chip、Badge、Alert、ProgressBar、ProgressCircle |
| 折叠技术信息 | Disclosure、Accordion |
| 主要和次要操作 | Button、ButtonGroup、Toolbar |
| 普通弹层 | Modal、Drawer、Popover |
| 危险确认 | AlertDialog |
| 短暂反馈 | Toast |
| 异步加载 | Skeleton、Spinner |
| 辅助说明 | Tooltip、Description、FieldError |

实现时必须遵循 HeroUI v3 约束：

- 使用 compound component anatomy。
- 不使用 v2 的 `HeroUIProvider`。
- 交互优先使用 `onPress`。
- Tailwind CSS v4 样式先导入，`@heroui/styles` 后导入。
- 使用语义 variant，不在业务组件中硬编码状态颜色。
- HeroUI 只提供无障碍基础，最终仍以 WCAG 2.2 AA 验证结果为准。

## 13. 视觉语言

### 13.1 风格方向

推荐采用克制、清晰的开发者控制台风格：

- 中性背景和清晰的信息层级。
- 避免大面积渐变、重阴影和装饰性插画。
- Card 主要通过边框和轻微背景差区分层级。
- 页面视觉重心放在服务状态、操作和数据，而不是品牌装饰。

### 13.2 色彩

- 品牌强调色使用冷蓝或蓝青色。
- success、warning、danger 使用 HeroUI 语义 token。
- `none` 鉴权、删除和不可恢复操作持续使用 danger 语义。
- operation running 使用 accent 或 warning，不能误用 success。
- light/dark 主题均使用 `oklch` CSS 变量。

具体色值在视觉稿阶段确定，本文不提前锁定未经验证的品牌色。

### 13.3 字体与数字

- 正文使用系统无衬线字体栈。
- service ID、endpoint、generation、revision、toolset、JSON 和 reason code 使用等宽字体。
- 日期按用户 locale 显示，并允许查看 UTC 原值。
- 状态名称、按钮文案、说明性文本随当前界面语言（中文/英文）切换；稳定枚举值和 reason code 始终保留英文原值，不参与翻译（见 14 章）。

### 13.4 尺寸

- 以 4px/8px 为基础间距单位。
- 普通 Card 圆角建议 10–12px。
- 表格默认采用中等或紧凑密度。
- 主要点击目标不小于 24×24 CSS px，常用按钮建议达到 36–40px 高度。

## 14. 国际化（中英文切换）

### 14.1 范围

第一版支持简体中文和英文两种界面语言，不规划其它语言。语言是界面展示层属性，不影响后端数据结构、API 字段名、稳定枚举值和 reason code。

### 14.2 语言来源与切换入口

- 语言偏好优先级：用户在顶部栏显式选择 > 浏览器/系统语言 > 平台默认（中文）。
- 登录后随账户持久化用户的语言偏好，跨设备生效；未登录页面（`/login`）按浏览器语言展示，不强制先登录才能看到英文。
- 切换入口统一放在顶部栏，与明暗主题切换相邻（见 4.2 节）；切换即时生效，不要求刷新整页或重新登录。

### 14.3 翻译边界

必须翻译：

- 导航、页面标题、按钮、Tab、表单 Label、说明文案、空态/错误态文案、Toast、AlertDialog 文案。
- 状态的用户可读解释（如"正在同步""已发布"）。

禁止翻译或改写：

- 稳定枚举值本身（`desired_status`、`runtime_status`、operation 状态、reason code 等的原始英文取值）。
- service ID、endpoint、generation、revision、toolset 等标识符。
- 用户输入内容：服务名称、描述、团队名称、用户名。
- audit_event 的 `action`/`resource_type` 原始值和 request_id。

这与第 3.1 节"状态真实"一致：翻译只作用于展示层的解释文字，不能让同一个稳定枚举在中英文下产生歧义或被误认为是两种状态。

### 14.4 布局适配

- 中英文文本长度差异明显，按钮、表格列宽、Tab、Chip 等不使用刚好贴合中文文案的固定宽度，需为英文文案预留合理的换行或省略空间。
- 表格优先使用 `fit_content`/`fill_container` 而非硬编码像素宽度，避免英文列标题被截断（对应第 8 节以外的通用表格实现要求）。
- 等宽字段（第 13.3 节）不受语言切换影响。

### 14.5 非目标

本节不定义具体的 i18n 资源文件格式、翻译流程或第三方翻译服务集成，这些属于前端实现细节，由 [06-frontend.md](architecture/06-frontend.md) 后续补充。

## 15. 可访问性

- 根文档 `lang` 属性随当前界面语言在 `zh-CN`/`en` 之间切换。
- 每页只有一个主要 `h1`。
- 提供 skip link、landmark 和 Breadcrumbs。
- 所有输入有持久 Label，placeholder 不替代 Label。
- 错误通过文本和 `aria-describedby` 关联，不只使用颜色。
- modal 打开后焦点进入，关闭后返回触发器。
- 后台轮询不无故抢焦点。
- 保存、复制和状态变化使用 live region 提示。
- 支持 `prefers-reduced-motion`、200% zoom 和系统高对比模式。
- 拖拽排序必须提供键盘上移/下移操作。
- 一次性 Key Modal 不自动关闭。

## 16. 响应式策略

| 宽度 | 策略 |
|---|---|
| `>= 1024px` | 完整 Table、两列概览、Schema 多栏工作台 |
| `640–1023px` | 隐藏低优先级表格列、概览改为单列或不等宽两列 |
| `< 640px` | 服务 Card 列表、单列表单、工具列表进入 Drawer |

响应式断点应根据内容测试调整，不把设备型号作为设计依据。

## 17. 加载、空、错误与恢复规范

| 场景 | 主要表现 | 恢复动作 |
|---|---|---|
| 首次加载 | 与最终布局等高的 Skeleton | 自动请求 |
| 后台刷新 | 保留旧数据，局部显示更新状态 | 手动重试 |
| 空列表 | 解释尚无服务 | 创建服务 |
| 筛选为空 | 说明无匹配结果 | 清除筛选 |
| 403 | 保留可读信息，禁用写操作 | 刷新权限 |
| 404 | 统一不存在或不可见 | 返回服务市场 |
| 409 | 保留草稿和冲突摘要 | reload 或 rebase |
| 422 | 顶部摘要和字段错误 | 定位并修正 |
| 429 | Retry-After 倒计时 | 到期后手动操作 |
| 502/503 | 区分上游与平台不可用 | 保留安全快照并重试 |
| operation failed | 显示旧 active 状态 | 编辑、重建或重同步 |

所有错误应允许复制 `request_id`，但不能显示堆栈、内部 URL、容器 ID、原始下游响应或秘密。
